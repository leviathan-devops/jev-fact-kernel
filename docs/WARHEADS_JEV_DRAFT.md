## WARHEAD 45 — THE JEV-DECISION LAW

THE LAW:
- ALWAYS ROUTE A JUDGEMENT THROUGH THE JUDGE. A judgement is any question whose answer is not mechanically derivable: classification, prioritisation, membership ("is this an instance of X?"), selection ("which of N applies?"), sufficiency ("is this evidence enough?"), or confidence. Run it through the judge — the `jev` tool (verb=`filter|find|decision-tree|route|evaluate`), the `jev_decide` MCP tool, or `jm decision-tree` — never through intuition. The judge is a LOCAL model on this host: no api key, no billing, no quota, ~100 ms warm, and N items cost ONE request. An important decision answered from intuition while the judge was reachable is an unverified decision.
- NEVER LET THE MODEL MAKE AN IMPORTANT DECISION WITHOUT THE JUDGE. The judge returns a CALIBRATED PROBABILITY; the CODE turns it into the decision. State the question, take the probability, apply the policy ladder — `p >= act (0.8)` → act, `p >= flag (0.5)` → escalate for review, below → noop. The model informs; the policy decides. A decision reported without its probability is an opinion wearing a verdict's clothes.
- ASK ONE THING PER QUESTION. A compound question ("is this a shipping failure or a defect that reached production?") makes the judge score a blend of two claims, and the blend lands mid-range — measured: a compound question's maximum never crosses 0.5, so it clears no real threshold and returns nothing; a sharp single claim measured max 0.949 with a 0.902 spread. Name the claim, not the topic: "does this text contain a specific bug report with a root cause?" discriminates; "shipping failure" does not, because everything about shipping is adjacent to it.
- WRITE THE CRITERIA SO HIGH MEANS THE THING YOU ASKED. The `criteria` field sets the probability's SIGN. Asking "is this theatrical?" while writing `criteria: {true: "the claim names real evidence"}` inverts the reading — a high score then means NOT theatrical, and a gate built on it does the opposite of what was intended, silently. Write the criteria so a HIGH value means the thing the question names. The field is `criteria`: a `choice` needs at least two options in it, a `score` needs a list of at least two levels, every question needs `instructions`. `options` is not a field — sending it yields a refusal that reads as a missing capability.
- DERIVE THE THRESHOLD — NEVER PICK IT. Sweep at least four thresholds and read the maximum and the spread before trusting any `min_p`. A spread above 0.25 means the question discriminates; a maximum below 0.5 means the QUESTION is broken, not the threshold. Lowering the threshold to catch a broken question admits the whole corpus and destroys the signal — the fix is the question, never the number.
- VALIDATE THE INSTRUMENT BEFORE BELIEVING ITS VERDICT. Run a POSITIVE control (an obvious instance) and a NEGATIVE control (an obvious non-instance) through the same question. Measured on a working judge: positive 0.915, negative 0.146 — a gap of 0.77. Without both controls a constant 0.5 is indistinguishable from a working judge, and a judge that never discriminates reads as a considered answer.
- REJECT THE REFUSAL THAT NAMES A TYPE; PROBE THE ENDPOINT. When a tool refuses a question type, probe the endpoint directly before believing the capability is absent. A documented prohibition can be a stale measurement taken against a different endpoint, or a malformed payload recorded as a missing capability — measured: a `choice` question was refused as unsupported while the endpoint accepted it and returned a full five-label distribution; the actual cause was the wrong field name in the request. A capability is absent when the ENDPOINT says so, never when a client's guard says so.
- BATCH — MANDATORY, AND MECHANICALLY VISIBLE. NEVER LOOP. N items are judged in ONE request — the `questions` map is caller-keyed, so N items become N questions in a single call. Measure it: the run reports `requests=1` for N judged items. `requests=N` for N items means the endpoint is the raw model backend rather than the adapter, and the caller is paying N round trips for work that takes one.
- NEVER REPORT A JUDGE OUTCOME WITHOUT ITS TWO NUMBERS. Every judged result carries the probability AND the threshold it was compared against. "It passed" is not a result; "p=0.87 against act=0.8, routed act" is. And never report a cost figure as a charge — a locally served judge bills nothing, and a vendor rate printed beside a local run is a savings figure.

## WARHEAD 46 — THE JEV-DATA-FLOW LAW

THE LAW:
- ALWAYS NARROW BEFORE YOU READ. Reading N files to find the few that matter spends the context window on material that was never going to be used. The order is fixed: index the corpus once, narrow it deterministically with the keyless verbs, judge the survivors, and read ONLY what survived. Measured on a real corpus: 349,396 lines indexed in 609 ms; a 21-term vocabulary census in 1.1 s; 100 candidates judged in one request at 21.9 s. An agent that reads 300 files to find 3 performed a scan the index answers instantly.
- ALWAYS RUN THE KEYLESS VERBS FIRST — THEY COST NOTHING. `query` (FTS or a SQL predicate), `scan` (keyword with excerpts), `extract` (regex into structured rows), `cluster` (signature groups) and `report` (index state) require no judge and never touch the model. Reach for a judged verb only when the question is genuinely semantic — is this a failure, is this a duplicate, should I act. A regex answers more questions than the reflex admits.
- LEARN WHICH VERB ANSWERS WHICH QUESTION. `query` for "where is this term" (ranked rows). `scan` for "show me the context around this term" (keyword + excerpts). `extract` for "pull every match into structure" (regex → rows). `cluster` for "what kinds of things are these" (signature groups). `filter` for "which of these are X" (judged, with probabilities). `find` for "where does X recur" (the 9-stage chain — patterns with support counts and exemplars). `decision-tree` for "classify all of these" (a recipe over N rows). `route` for "which tool handles this task". `push-gate`, `st-detect` and `spec-audit` for mechanical verdicts with exit codes. Naming the wrong verb wastes as much as not using the tool.
- NEVER HAND-SEARCH A CORPUS YOU CAN INDEX. `grep` over a tree you have already indexed, a manual list-and-read sweep, a shell loop extracting a field from every file — each performs at hand what `query`, `extract` or `cluster` performs in one call over the whole corpus. Index first; the index is incremental by content hash, so re-indexing after a change costs only what changed.
- READ THE TREND, NOT JUST THE OUTPUT. Every `find` run reports its chain — `seeds → candidates → kept → patterns` — followed by `N judged · M kept · R requests`. `R=1` for N items is healthy. `R=N` means the endpoint is the raw model backend and the run is paying N round trips; fix the endpoint before trusting the result. `M=0` with a non-zero judge count is a QUESTION defect, not an empty corpus.
- TREAT ZERO KEPT AS AN ALARM, NEVER AS AN ANSWER. Before concluding "nothing matches", check three things: did the judge actually run (`calls` above zero), was the question a single sharp claim (a compound question caps below any real threshold), and was the threshold derived rather than picked. An unexamined `kept=0` reports a fact about the question as though it were a fact about the corpus.
- ALWAYS LOOK FOR THE JEV-SHAPED WORK BEFORE STARTING A MANUAL PASS. The trigger is a plan containing any of: reading more than a handful of files to find some, searching a corpus for a term or a pattern, extracting a field across many documents, grouping or counting a body of records, answering a yes/no about a set of texts, or classifying a set of records. On that trigger, name the verb that answers it and run it FIRST. The failure this prevents: spending a context window on a manual scan that an indexed call resolves in a second — the work was not hard, it was routed wrong.
- ALWAYS KEEP THE STORE DISPOSABLE — NEVER PIN A PROBE TO IT. Point `JM_HOME` at a scratch directory for one-off triage so probe indexes never accumulate in the operator's real store — measured failure: hundreds of megabytes of probe indexes silently filled a shared store. The store is rebuildable by design (incremental by content hash); the corpus is not.
- NEVER PRESENT A NARROWED SET AS THE WHOLE. When the result is a filtered subset, state the filter — the index name, the query, the threshold, and the count that survived. A list of twelve rows with no denominator reads as a complete account of the corpus, and the exclusion is invisible to whatever consumes the list.
